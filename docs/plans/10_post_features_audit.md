## F1 — Medium: длинная подпись к одиночному медиа теряется молча
**Где:** `app/bot/presentation.py` (блок `media` с 1 элементом и `voice`) →
`sender.send_media_item(caption=b.text)`. Telegram ограничивает **caption медиа 1024
символами** (текст сообщения — 4096). Если менеджер напишет длинную подпись, Telegram
вернёт 400, блок упадёт в `except` (best-effort) и **молча пропустится** — клиент не
увидит ни медиа, ни текст, а менеджер не узнает.

**Как чинить:** в `send_media_item`/презентации — если `caption` длиннее ~1024:
отправить медиа **без** подписи, а текст — отдельным сообщением (как уже сделано для
`media_group` и `video_note`). Это та же логика, что в воркере воронок для альбомов.
Плюс — в админке мягко предупреждать при вводе >1024 символов в подпись медиа-блока.
Тривиально, 1 хелпер + ветка.

## F2 — Medium: `cancel_reason` не очищается
**Где:** `app/api/leads.py::update_lead`. При переводе заявки из `cancelled` обратно
в `new/contacted/paid` поле `cancel_reason` (и `cancelled_at`) **остаётся заполненным**.
На аналитику не влияет (summary фильтрует `status=='cancelled'`), но на карточке заявки
покажется неактуальная «причина отмены».

**Как чинить:** в `update_lead`, если новый статус ≠ `cancelled` — занулять
`lead.cancel_reason = None` (и опц. `cancelled_at`). 2 строки + тест.

## F3 — Low: гранулярность аудита вложенных ресурсов
**Где:** `app/api/middleware/audit.py`. `POST /payments/{id}/receipts` пишется как
`resource_type=payment, action=create` (не «receipt»); `POST /products/{id}/content-blocks`
→ `product/create`. Поле `path` сохраняет точный URL, так что **информация не теряется**,
но фильтр по `resource_type` не различает «платёж» и «чек платежа».

**Как чинить (если нужно):** маппинг вложенных путей (`.../receipts`→`payment_receipt`,
`.../content-blocks`→`product_content_block`) по предпоследнему сегменту. Опционально —
по необходимости заказчика. Сейчас приемлемо.

## F4 — Low: нормализация resource_type
**Где:** `_RESOURCE_BY_SEGMENT` не содержит `content-blocks`, `content-block-media` →
в аудит пишется множественное «content-blocks». Косметика, фильтр работает.
**Как чинить:** добавить ключи в маппинг.

## F5 — Low: orphan-файлы чеков/медиа при сбое commit
**Где:** `payments.create_payment::_save_staged_receipts` и
`product_content.upload_media` пишут файл на диск **до** `session.commit()`. Если commit
упадёт — на диске останется «висячий» файл без строки в БД. Данные не теряются, утечки
секретов нет — просто мусор на диске.
**Как чинить (если важно):** периодическая GC-задача чистящая файлы без строк, либо
писать файл после успешного flush в try/except с удалением при откате. Низкий приоритет.

## F6 — Low/cosmetic: мёртвые импорты
**Где:** `app/bot/handlers/core.py` импортирует `_send_catalog`, `_send_product_card`,
`_product_kb` — после перевода `/start` на `_send_main_menu`/`present_product` они в
core больше не используются (живут в `common.py`/`leads.py`). Не баг, лишний шум.
**Как чинить:** убрать неиспользуемые импорты (ruff подсветит).

## F7 — Low/perf: лишние DB-сессии
**Где:** (а) `AuditMiddleware` открывает отдельную `SessionLocal()` + commit на каждую
мутацию; (б) `presentation._persist_file_id` открывает сессию на **каждый** сохраняемый
file_id. Корректно, но под нагрузкой — давление на пул соединений.
**Как чинить (если нужно):** батчить сохранение file_id одной сессией в конце презентации;
аудит можно оставить (1 запись на мутацию — норм). Низкий приоритет.
